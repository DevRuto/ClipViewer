# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ClipViewer is a self-hosted video clip sharing service (like a minimal Streamable/YouTube) — upload a
video, it gets transcoded to HLS in the background, and it's playable/shareable via a link for as long
as the server runs. It's a personal side project with no long-term maintenance commitment; keep changes
minimal and pragmatic rather than over-engineered.

## Architecture

Three .NET 10 projects + one Vue 3 SPA, backed by PostgreSQL:

- **ClipViewer.API** — ASP.NET Core web API + hosts the built Vue SPA as static files. Handles auth,
  video CRUD, and file uploads. Does **not** transcode video itself.
- **ClipViewer.Worker** — a separate background-service process (`BackgroundService`) that polls the
  database for pending conversion jobs and does the actual FFmpeg work (via `Xabe.FFmpeg`).
- **ClipViewer.Data** — shared EF Core `ApplicationDbContext` and entity models, referenced by both
  API and Worker.
- **clipviewer.vue** — the Vue 3 + Tailwind v4 frontend, built to `clipviewer.vue/dist` and served by
  the API in production (proxied to Vite dev server on `:5173` in development).

**Job flow (important, spans multiple files):** the API and Worker are decoupled entirely through the
Postgres database — there is no in-process queue or message broker. `UploadController` saves the raw
upload to a temp folder and calls `IVideoJobQueue.EnqueueAsync` (`VideoJobQueue.cs`), which writes a
`VideoClip` row (unprocessed) and a `VideoConversionJob` row (`Status = "Pending"`) to the DB. The
Worker's `VideoConversionWorker` polls `VideoConversionJobs` every second for the oldest `Pending` job,
marks it `Processing`, trims (if requested) and transcodes to HLS + generates a thumbnail via FFmpeg,
then updates the corresponding `VideoClip` and marks the job `Completed`/`Error`. Job progress is
written back to the DB as FFmpeg reports it, which is how the frontend can poll for conversion progress.

**Auth:** dual-scheme — JWT bearer for the SPA (`AuthController` exchanges an API key GUID for a JWT)
and a raw `X-API-Key` header scheme (`ApiKeyAuthMiddleware.cs` / `ApiKeyAuthHandler`) for
programmatic/API use (e.g. uploading via `scripts/create_user.sh`-provisioned keys). A policy scheme
(`JwtOrApiKey`) picks between them based on whether an `Authorization: Bearer` header is present.
Users are created out-of-band via `scripts/create_user.sh` / `scripts/update_user.sh` (direct DB
scripts) — there is no signup endpoint. Admins can create/manage other users and rotate their keys via
the `/api/users` endpoints (`UsersController`, `[Authorize(Roles = "Admin")]`); `scripts/set_user_role.sh`
promotes/demotes a user's role directly against the DB, which is how the first Admin gets bootstrapped.

**File serving:** uploaded/converted media lives on disk under `UploadOptions:OutputVideoFolder`
(`./output` by default: `output/source`, `output/hls/{videoId}/playlist.m3u8`, `output/thumbnails`) and
is served as static files under `UploadOptions:PublicFilePath` (`/files`). Both API and Worker read the
same `UploadOptions` config section and must agree on this path (in Docker it's a shared volume mount).

**videoId** is a short random base64 string (not the DB GUID) generated by `VideoJobQueue`, used in
URLs/filenames; the DB row `Id` (Guid) is internal only.

## Commands

### Backend (.NET, run from repo root)
```sh
dotnet build ClipViewer.sln                  # build everything
dotnet run --project ClipViewer.API          # run the API (also proxies to Vite in dev)
dotnet run --project ClipViewer.Worker       # run the conversion worker (needs FFmpeg on PATH + DB)
dotnet test ClipViewer.UnitTests             # run unit tests (fully isolated, all collaborators mocked)
dotnet test ClipViewer.IntegrationTests      # run integration tests (real EF Core InMemory DbContext, file I/O, or a live BackgroundService loop)
dotnet test ClipViewer.UnitTests --filter FullyQualifiedName~AuthControllerTests.MethodName  # single test
```
`ClipViewer.UnitTests` and `ClipViewer.IntegrationTests` are separate projects on purpose: anything that touches a
real `ApplicationDbContext` (even InMemory), the filesystem, or a timing-based wait (e.g. polling a
`BackgroundService`) belongs in `ClipViewer.IntegrationTests`, not `ClipViewer.UnitTests` — keeps the unit suite
fast and deterministic.

EF Core migrations (run from repo root):
```sh
dotnet ef migrations add <Name> --project ClipViewer.API --startup-project ClipViewer.API --context ApplicationDbContext
dotnet ef database update --project ClipViewer.API --startup-project ClipViewer.API --context ApplicationDbContext
```
The API auto-applies pending migrations on startup (`context.Database.Migrate()` in `Program.cs`), so
`database update` is mainly useful for local inspection/rollback.

### Frontend (`clipviewer.vue/`)
```sh
npm install
npm run dev             # Vite dev server on :5173
npm run build            # production build to dist/, consumed by the API
npm run lint             # eslint --fix --cache
npm run format            # prettier --write src/
npm run test              # vitest (tests/unit + tests/integration)
npm run test -- <pattern> # run a single test file/pattern
npm run test:coverage
```

### Docker (full stack: db + api + worker)
```sh
docker compose up --build
```
Serves the app at http://localhost:5000; Postgres on 5432. `./output`, `./logs`, `./worker-logs` are
bind-mounted so API and Worker share the same media files. `scripts/create_user.sh` /
`scripts/update_user.sh` connect to the compose Postgres container to provision/rotate a user's API key.
`scripts/backup_db.sh` dumps the compose Postgres database to `db_backup/`.

## Notes

- Non-Development, non-Production environments (e.g. the default `dotnet test`/design-time context) use
  an EF Core in-memory database instead of Postgres — see the `builder.Environment.IsDevelopment() ||
  IsProduction()` check in `ClipViewer.API/Program.cs`.
- Both API and Worker independently ensure `UploadOptions:TempVideoFolder` /
  `OutputVideoFolder` exist on startup — if you add a new project that touches those folders, mirror
  that setup.
- `docs/ENDPOINTS.md` has example request/response payloads for the video endpoints.
